# Week 4 — 통합 시나리오 검증 결과 (경계값 10종)

`./run.sh --week4` 앱에서 애매한 경계 질문 10개를 입력해, LLM이 출처(참고자료 references / 저장기록 saved_requests)를 올바르게 라우팅하고 근거(hits/rows)로 답하는지 확인했다. 라우팅은 프롬프트+docstring 기반이라 확률적이므로, "정답"보다 **어느 tool로 갔고 근거로 답했는지**를 관찰한다.

## 준비
- 참고자료(references): seed 3건 — 집중 회의 선호(오전 10~12시) / 점심 보호(12~13시) / 팀 싱크(60분·아젠다).
- 저장기록(saved_requests): `디자인 리뷰 회의`(group_schedule, 2026-07-23 15:00) 저장.
- 기준일: 2026-07-22.

## 관찰된 특이점 3건 (원인 가설)

### ⚠️ #5 "금요일 오후에 미팅 잡아도 돼?" — 선호 확인 없이 일정 생성으로 해석
- 현상: `extract_schedule_request`로 가서 "13:00 가능, 등록할까요?"라 답함. "금요일 오후 외부 미팅은 안 잡는다"는 참고자료를 **참조하지 않음** → 규칙과 반대되는 "가능" 답변.
- 가설: "미팅 잡아도 돼?"의 "잡"이 일정 생성 신호로 강하게 읽혀, 참고자료 확인 단계를 건너뜀.
- 개선안(옵션): 프롬프트에 "일정을 잡거나 가능 여부를 답하기 전에, 관련 선호/규칙 참고자료를 먼저 확인한다" 규칙 추가.

### ⚠️ #3 "팀 회의 관련 정보 알려줘" — 참고자료를 안 봄
- 현상: `search_saved_requests`(SQL)만 호출 → 저장기록 없어서 "없음". 하지만 seed에 "팀 싱크" 참고자료가 있어 references였다면 유용했음.
- 가설: "팀 회의"의 "회의"가 저장기록 쪽 신호로 읽힘. 진짜 모호한 케이스라 한쪽만 선택.
- 개선안(옵션): 모호할 때 두 출처를 모두 검색하도록 프롬프트 유도(가이드도 "둘 다 선택 가능" 명시).

### ⚠️ #8 "내일 일정 뭐야?" — group_schedule을 놓침
- 현상: `personal_list_saved_schedules`가 기본 `kind=personal_schedule`이라, 내일(07-23)에 있는 디자인 리뷰(group_schedule)를 조회에서 제외 → "없음".
- 성격: **버그가 아니라 스펙**(가이드 "기본 kind=personal_schedule"). 다만 "내일 일정 전체"를 물으면 개인 일정만 봐서 놀랄 수 있는 한계.
- 개선안(옵션): "종류를 특정하지 않은 조회는 kind 필터 없이 전체를 본다"는 규칙, 또는 tool에 kind=None 허용.

### ✅ #10 — 지어내지 않기(가장 중요한 성공)
- 무관한 참고자료만 hit(distance 1.6+)됐는데도 "저장된 내용 없음"이라 정직하게 답함. M4 프롬프트의 "근거 없으면 지어내지 말라"가 실제로 작동.

## 개선 조치 (프롬프트 규칙 추가)
`week04_prompt_parts`에 경계 교정 규칙 3개 추가:
- ④ 일정 생성/가능여부("~해도 돼?") 답변 전에 관련 선호·규칙을 참고자료에서 먼저 확인 → **#5 대상**
- ⑤ 출처가 모호하면 참고자료+저장기록을 모두 검색해 종합 → **#3 대상**
- ⑥ 종류 불특정 일정 조회는 개인만 보지 말고 저장기록 전체를 확인 → **#8 대상**

### #5 후속 조치 (리뷰 피드백 반영)
리뷰에서 "검색 결과가 부족할 때의 후속 전략"에 대한 질문을 받아, 원인을 다시 측정했다.

같은 메모를 두고 질의 표현만 바꿔 검색한 결과:

| 질의 | "금요일 오후엔 외부 미팅을 잡지 않는다" 순위 |
|---|---|
| "금요일 오후에 미팅 잡아도 돼?" (사용자 원문) | 1위 (distance 0.771) |
| "금요일 미팅" | 1위 (0.900) |
| "미팅" | 1위 (1.344) |
| **"미팅 선호 시간"** (LLM이 실제로 사용한 질의) | **4위 (1.505)** → top_k=2에서 잘림 |

즉 원인은 검색량(top_k)보다 **LLM이 질의를 일반적인 표현으로 바꿔 쓴 것**이었다. 이에 두 층으로 조치했다.

1. **프롬프트**: 참고자료 검색 질의에 사용자 문장의 구체 조건(요일·시간대·대상)을 그대로 남기도록 규칙 추가(⑦). 근거가 약하면 같은 질의로 개수만 늘리지 말고 질의를 더 구체적으로 바꿔 재검색하거나 못 찾았다고 답하도록 규칙 추가(⑧).
2. **코드**(`search_personal_references`): ⑴ 최소 후보 수 확보(top_k가 작아도 4건은 조회) ⑵ 최상위 distance가 1.5를 넘으면 근거 부족으로 판단 ⑶ 판단 결과를 `retrieval`(best_distance/sufficient, 부족할 때 hint)로 함께 반환해 trace에서 확인 가능.
   - 임계값 1.5는 실측 분포에서 정했다: 관련 질의 0.77~1.13, 경계 1.46, 무관 질의 1.62 이상.

### 후보 확장 vs 질의 재작성 비교 측정
처음에는 근거가 부족하면 같은 질의로 후보를 넓혀 재검색하도록 구현했으나, 리뷰에서 "최상위 distance가 이미 임계값을 넘었다면 개수만 늘려도 최상위 품질은 좋아지지 않고 무관한 자료만 늘어난다"는 지적을 받아 두 전략을 직접 비교했다.

| 상황 | 전략 | best distance | 무관 자료(>1.5) | 타깃 메모 |
|---|---|---|---|---|
| 관련 자료 있음 / 질의가 일반적 ("미팅 선호 시간") | 원본 top_k=2 | 1.382 | 0건 | 미포함 |
| | 후보 확장 top_k=8 | **1.382 (변화 없음)** | 0 → 1건 | 4위 |
| | 질의 재작성 ("금요일 오후 외부 미팅") | **0.547** | 0건 | **1위** |
| 관련 자료 없음 ("김치찌개 레시피") | 원본 top_k=2 | 1.711 | 2건 | — |
| | 후보 확장 top_k=8 | 1.711 (변화 없음) | 2 → 4건 | — |
| | 질의 재작성 | 1.723 (개선 없음) | 2건 | — |

- 후보 확장은 어느 경우에도 최상위 관련도를 개선하지 못했고, 무관한 자료 수만 늘렸다.
- 질의 재작성은 관련 자료가 있을 때 최상위 distance를 1.382 → 0.547로 낮추고 타깃을 1위로 올렸다.
- 관련 자료가 아예 없으면 두 전략 모두 의미가 없으므로 "근거를 찾지 못했다"고 답하는 것이 맞다.

이 결과에 따라 코드에서 확장 재검색을 제거하고, `sufficient=false`일 때는 판단 결과와 안내(hint)만 반환해 질의 재작성이나 "못 찾음" 답변으로 이어지도록 바꿨다. 순위에서 잘리는 문제(관련 자료가 있지만 top_k 밖)는 최소 후보 수 확보가 담당하므로, 두 대응은 서로 다른 문제를 다룬다.

조치 후 재측정:

| 입력 | 조치 전 | 조치 후 |
|---|---|---|
| "미팅 선호 시간" (top_k=2) | 상위 2건에 금요일 메모 없음 | returned=4, **금요일 메모 포함**, sufficient=true |
| "김치찌개 레시피" (무관) | 무관한 hit만 반환 | best=1.711 → **sufficient=false, widened=true** (근거 부족 신호) |

### #5 최초 관찰 기록
- 규칙 ④ 이후 동작 변화: 가능여부를 답하기 전에 `search_personal_references`를 실제로 호출함(개선 전에는 호출하지 않음).
- 검색 결과: 질의 "미팅 선호 시간" + top_k=2 기준 상위 2건은 seed의 점심(1.382)·팀싱크(1.442) 메모였고, 사용자가 저장한 "금요일 오후엔 외부 미팅을 잡지 않는다" 메모는 상위 2건에 포함되지 않았음.
- 그 결과 최종 답변은 점심 규칙만 반영해 "오후 1시 이후 가능"으로 나옴.
- (사용자 메모는 준비 단계에서 저장 완료, 새 대화에서 실행함.)

### #5 재교정 (규칙 ④ 강화)
규칙 ④가 있었지만 모델이 이를 건너뛰고 "저장된 일정이 비었으니 가능"으로 답하고 있었다. 규칙을 명령형으로 바꾸고 금지 사항을 명시했다.

- 가능 여부를 묻는 질문에는 **다른 tool보다 먼저** `search_personal_references`를 호출한다.
- 저장된 일정이 비어 있다는 것만으로 "가능하다"고 답하지 않는다.
- 참고자료의 제약을 답변에 그대로 언급한다.
- 가능 여부 질문은 일정 확정 요청이 아니므로 저장 tool을 호출하지 않는다.

| | 강화 전 | 강화 후 (2/2) |
|---|---|---|
| 호출 tool | `extract_schedule_request` + `search_saved_requests` | **`search_personal_references`만** |
| 금요일 메모 | 검색 결과에 없음 | **검색 결과에 포함** |
| 답변 | "금요일 오후에 미팅을 잡으셔도 됩니다" | **"금요일 오후에는 외부 미팅을 잡지 않는다는 개인 규칙이 있습니다 … 어려울 것 같아요"** |

### 프롬프트로 재검색을 강제할 수 없었던 부분
리뷰에서 "`retrieval_hint`가 재검색을 유도할 수는 있어도 실제 재호출을 보장하지는 않는다"는 지적도 받았다. 규칙 ⑧을 "반드시 한 번은 질의를 바꿔 다시 검색한 뒤 결론을 낸다"로 강화하고 근거 없는 질문("내가 좋아하는 음식이 뭐라고 적어뒀지?")으로 2회 측정한 결과:

- 참고자료 검색은 **1회만** 호출되고 재검색은 일어나지 않았다.
- `sufficient=false`는 정상적으로 관측됐고, 답변은 "기록을 찾지 못했습니다"로 **지어내지 않았다**.

즉 프롬프트 규칙은 재검색을 보장하지 못했다(지적이 맞았다). 대신 근거 부족을 인지하고 사실을 만들어내지 않는 동작은 지켜졌다. 회귀 테스트는 이 실측에 맞춰 **"질의를 바꿔 재검색하거나, 지어내지 않고 못 찾았다고 답한다"** 중 하나를 만족하는지로 검증한다.

### 테스트 데이터 정리 방식 변경
"생성 시각 이후 row 삭제" 방식은 테스트 중 다른 경로가 만든 실제 데이터까지 지울 수 있다는 지적을 받아, **저장 tool 결과에서 이번 실행이 만든 `request_id`/`schedule_id`만 뽑아 삭제**하도록 바꿨다. 회귀 테스트가 필요한 근거 데이터(내일 group_schedule, 금요일 규칙 메모)도 테스트가 직접 심고 자기가 만든 id만 지운다.

## 결론
- 명확한 케이스(1·2·4·6·7·9·10)는 의도대로 동작. 특히 #10은 무관한 검색 결과에도 지어내지 않고 "없음"으로 답함.
- 경계 케이스 #3·#8은 규칙 ⑤·⑥으로 교정되어 재측정에서도 유지됐고, #5는 규칙 ④를 명령형으로 강화한 뒤 교정됐다.
- 세 케이스 모두 `tests/test_week04_e2e.py`의 회귀 테스트로 고정했다(입력은 실패 당시 그대로, 검증은 tool 호출뿐 아니라 검색 결과·답변 반영까지).
- 프롬프트로 보장되지 않는 동작(근거 부족 시 재검색)은 강제하지 못했고, 대신 "지어내지 않는다"를 검증 대상으로 삼았다.

## 5주차 작업 중 발견 — 규칙 ⑥ 라우팅이 앱 날짜에 따라 뒤집힘 (2026-07-30)

5주차 구현 후 전체 테스트를 돌렸을 때 `test_e2e_regression_unspecified_kind_includes_group_schedule`가 3회 연속 실패했다. 5주차 코드가 원인인지 먼저 확인했고, 아니었다. 이 테스트는 week04 자체 agent(`week04_retrieve_nanas_memory.build_week_agent`)를 쓰고, 5주차 모듈은 호출 경로에 없다.

### 측정 — 질의와 코드를 고정하고 앱 날짜만 바꿈

질의 `"내일 일정 뭐야?"`, 각 2회 실행.

| 앱 날짜 | 호출된 tool | 규칙 ⑥ |
| --- | --- | --- |
| 2026-07-29 (4주차 측정일) | `list_saved_requests` | 준수 |
| 2026-07-30 (5주차 작업일) | `personal_list_saved_schedules` | 위반 |

`temperature=0`이라 프롬프트가 같으면 결과도 같다. 프롬프트에는 `current_app_date_iso()`로 오늘 날짜가 들어가므로, 날짜가 바뀌면 프롬프트 문자열이 바뀌고 경계에 있던 tool 선택이 뒤집힌다. 간헐적으로 흔들리는 flaky가 아니라 **코드를 바꾸지 않아도 날짜만으로 초록에서 빨강이 되는** 형태다.

### 보강 과정 (2단계)

1차로 `personal_list_saved_schedules`를 쓰지 말라고 명시했다. 2026-07-30은 교정됐지만, 2026-07-29에서는 모델이 형제 tool인 `personal_list_schedules`(1~2주차 현재 대화 임시 메모리 전용)로 옮겨갔다(2/2). 하나만 막으니 인접한 tool을 골랐다.

2차로 두 tool을 모두 이름으로 금지하고, 각각 무엇을 놓치는지와 대신 부를 tool·인자(`list_saved_requests`에 `date_from`/`date_to`만 넘기고 `kind`는 비움)를 함께 적었다. 재측정에서 두 날짜 모두 `list_saved_requests`를 호출했다(각 2회, 4/4).

### 관찰

- 금지 규칙은 "무엇을 쓰지 말라"만으로 부족했고, **"대신 무엇을 어떤 인자로 쓰라"**를 같이 적어야 인접 tool로 옮겨가지 않았다.
- e2e 라우팅 테스트는 프롬프트에 날짜가 들어가는 한 날짜 의존성을 가진다. 어제 통과한 테스트가 오늘 실패할 수 있다는 뜻이므로, 실패를 발견하면 먼저 "코드가 바뀌었는가"와 "입력이 바뀌었는가"를 구분해야 한다.
- 재현 방법: 앱 날짜는 `fixed/runtime_clock.py`의 `APP_TODAY`에 고정되고 `current_app_date()`가 호출 시점에 그 값을 읽는다. 이 값을 바꾸고 agent 캐시(`_WEEK04_AGENT`)를 비운 뒤 다시 만들면 같은 실험을 재현할 수 있다.
