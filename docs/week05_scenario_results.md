# Week 5 시나리오 검증 결과

`./run.sh --week5`로 앱을 띄우고 **직접 입력해 확인한 내용만** 기록한다. 자동 검증은 테스트가 담당한다.

| 수단 | 담당 |
| --- | --- |
| `tests/test_week05_mcp.py` (유닛 70) | 계약·경계·병합 로직을 매번 동일하게 확인 |
| `tests/test_week05_e2e.py` (e2e 10) | "이 문장 → 이 tool 호출"의 반복 확인, 회귀 고정 |
| 이 문서 | 수동 검증에서 새로 발견한 것, 답변 품질, 실행 편차 |

수동 검증에서 실패를 발견하면 문서에만 남기지 않고 **e2e 회귀 테스트로 옮긴다.** 문서는 *무엇을 발견했나*, 테스트는 *다시 깨지지 않게*.

## 확인 환경

- 실행일 기준 앱 오늘 날짜: **2026-08-02** (OS 날짜를 import 시점에 고정)
- 외부 실습 데이터: 멤버 `철수·영희·민준·서연·지훈·하린`, 일정 18건, 구간 **2026-07-07 ~ 2026-07-17**
- 실습 구간은 **과거**다. 날짜를 명시한 질문과 상대 표현 질문을 모두 확인했다.
- 확인 위치: Details 탭의 `tool_call` / `tool_result` trace
- 앱에서는 대화가 이어지므로, 앞 질문의 답이 다음 판단에 영향을 준다. 시나리오 16·17이 실제로 그 영향을 받았다.

## 1차 검증 (프롬프트 보강 전)

### 시나리오 1: "철수가 예전 대화에서 무슨 얘기 했는지 찾아줘"
- trace: `search_previous_conversations(query="철수")` → 1건
- 판정: 통과
- 관찰: 질의가 한 단어라 부분 문자열 대조에 걸렸다.

### 시나리오 2: "우리가 저번 대화에서 무슨 얘기했는지 찾아줘"
- trace: `search_conversation_messages(query="무슨 얘기")` → 3건 (distance 1.47 / 1.52 / 1.62)
- 판정: 통과
- 관찰: 1번과 문장 구조가 비슷한데 출처를 바꿔 골랐다. 이름이 비슷한 두 tool의 구분(규칙 ⑨)이 작동했다. 다만 distance는 1.5 안팎으로 관련도가 높지 않다. 질의가 모호했기 때문으로 보인다.

### 시나리오 3: "철수의 이전 대화 원문 메시지를 그대로 보여줘"
- trace: `search_previous_conversations(query="철수")` → `load_conversation_messages(conversation_id="ext_cs")`
- 판정: 통과
- 관찰: `conversation_id`가 앞 검색 결과에 있던 실재 값이다. 순서를 강제하지 않았는데도 검색 → 로드 순으로 진행했다.

### 시나리오 4: "2026년 7월 7일부터 17일까지 철수와 영희가 언제 바쁜지 알려줘"
- trace: `extract_schedules_from_history(["철수"])` + `extract_schedules_from_history(["영희"])` (병렬 2회) → 각 3건
- 판정: 통과
- 관찰: 한 번에 `["철수","영희"]`로 부를 수 있는데 멤버별로 나눠 불렀다. 결과는 정확하지만 MCP 서브프로세스가 2배로 뜬다.

### 시나리오 5: "같은 기간에 나와 철수가 각각 언제 바쁜지 정리해줘"
- trace: `collect_member_schedules(["철수","나나"])` + `collect_member_schedules(["나나"])`
- 판정: 부분
- 관찰: `"나나"`는 비서 이름이지 외부 멤버가 아니라서 외부 저장소에 없다. 내 일정은 `member_names`와 무관하게 합쳐지므로 결과 자체는 틀리지 않았지만, 호출이 한 번 낭비됐다.
- 후속: 규칙 ⑫에 "member_names에는 외부 멤버만" 추가 → 재측정에서 교정 확인

### 시나리오 6: "공유 일정 저장소에 등록되어 있는 일정을 보여줘"
- trace: `list_shared_schedules()` (필터 없음) → 18건
- 판정: 통과
- 관찰: 필터가 없을 때 저장소가 기본 실습 멤버·기본 구간으로 대체하는 분기가 의도대로 동작했다.

### 시나리오 7: "7월 15일에 바쁜 팀원이 누구야?"
- trace: `list_shared_schedules(date_from="2026-07-15", date_to="2026-07-15")` → 2건 (서연·철수)
- 판정: 통과
- 관찰: 멤버를 모르는 질문인데 `member_names`를 **빈 목록으로 넘기지 않고 생략**했다. `member_names`가 필수인 `extract_schedules_from_history` 대신 선택인 `list_shared_schedules`를 고른 것도 맞는 판단이다.

### 시나리오 8: "지민이 7월에 언제 바빠?"
- trace: `search_previous_conversations(query="지민 7월 일정", member_names=["지민"])` → 0건
- 답변: "지민님의 7월 일정에 관한 대화 기록이나 일정 정보를 찾을 수 없습니다."
- 판정: 부분
- 관찰: 답은 맞다(지민은 실습 데이터에 없다). 그러나 질의를 여러 단어로 이어 붙여 물었기 때문에, **지민이 실재했더라도 0건이 나왔을 방식**이다. 지어내지 않은 점은 정상.

### 시나리오 9: "다음 주에 철수 언제 바빠?"
- trace: `list_shared_schedules(["철수"], 2026-08-03 ~ 2026-08-09)` → 0건
- 답변: "다음 주(2026년 8월 3일부터 9일까지) 철수님의 바쁜 일정은 없습니다."
- 판정: 통과
- 관찰: 상대 표현을 오늘(2026-08-02) 기준으로 환산하고, **확인한 구간을 답변에 명시**했다(규칙 ⑮).

### 시나리오 10: "철수가 7월 9일에 뭐 한다고 했지? 그거 확정된 거야?"
- trace: `search_previous_conversations(query="철수 7월 9일 일정")` → 0건
- 답변: "이전 대화 기록을 찾지 못했습니다. 따라서 그 일정이 확정되었는지 여부도 확인할 수 없습니다."
- 판정: **실패**
- 관찰: 데이터는 존재한다. 철수 대화에 "7월 9일 14시는 고객 인터뷰"가 그대로 들어 있고 시나리오 1·3에서 같은 대화를 찾았다. 이 검색은 `LIKE '%query%'` **부분 문자열 대조**라, 여러 조건을 이어 붙인 질의는 통으로 일치하지 않으면 0건이 된다.
- 후속: 규칙 ⑩·⑭ 보강 → 재측정에서 사용자가 받는 답은 교정됐으나 원인은 남음(아래 참조)

### 시나리오 11: "철수가 고객 인터뷰에 대해 뭐라고 말했는지 원문 그대로 보여줘"
- trace: `search_previous_conversations(query="고객 인터뷰", limit=5)` → 1건
- 판정: 통과
- 관찰: 질의가 짧아 검색에 성공했다. 다만 "원문"을 요청했는데 `load_conversation_messages`는 호출하지 않았다. 검색 결과의 `content`에 원문이 들어 있어 답변은 가능했다.

### 시나리오 12: "영희가 발표 리허설 준비에 대해 뭐라고 했는지 찾아줘"
- trace: `search_previous_conversations(query="발표 리허설 준비", member_names=["영희"])` → 0건
- 답변: "지난 대화에서 찾을 수 없습니다. 다른 표현이나 더 구체적인 내용을 알려주시면 다시 찾아보겠습니다."
- 판정: **실패**
- 관찰: 영희 대화에는 "7월 16일 15시는 발표 리허설입니다"가 있다. **`"준비"` 한 단어** 때문에 부분 문자열 대조가 깨졌다. 시나리오 10과 같은 원인이고, 이번에는 재검색도 하지 않았다.

### 시나리오 13: "7월 7일부터 17일까지 나랑 영희, 민준이 각각 언제 바쁜지"
- trace: `collect_member_schedules(["영희","민준"], 7/07~7/17)` → 6건 (단일 호출)
- 판정: 통과
- 관찰: 비서 이름이 섞이지 않았고 호출도 한 번이다. 시나리오 5 대비 개선.

### 시나리오 14: "그 기간에 나만 언제 바쁜지 알려줘"
- trace: `list_saved_requests(date_from="2026-07-07", date_to="2026-07-17")` → 0건
- 판정: 통과
- 관찰: 내 일정만 필요할 때 외부 MCP tool이 아니라 앱 저장기록 조회로 간 것이 맞는 판단이다.

### 시나리오 15: "ext_zz 대화 내용 보여줘"
- trace: tool 호출 없음
- 답변: "대화 ID 'ext_zz'에 해당하는 대화 내용은 현재 조회할 수 없습니다."
- 판정: 부분

### 시나리오 16: "7월 17일에 바쁜 사람 있어?"
- trace: `collect_member_schedules(["영희","민준"], 7/17~7/17)` → 0건
- 답변: "영희와 민준 모두 바쁜 일정이 없습니다."
- 판정: **실패**
- 관찰: 하린이 7월 17일 09:00-10:00 회고 준비로 바쁘다. 대상을 지정하지 않은 질문인데 **앞 대화(시나리오 13)의 영희·민준으로 범위를 좁혔다.** 같은 성격의 시나리오 7은 새 대화에서 물어 통과했으므로, 대화 맥락 오염이 원인이다.

### 시나리오 17: "7월 6일에 바쁜 사람 있어?"
- trace: **tool 호출 없음**
- 답변: "영희, 민준, 사용자 모두 바쁜 일정이 없습니다."
- 판정: **실패**
- 관찰: 조회 없이 앞 결과로 추론해 단정했다. 7월 6일이 실제로 비어 있어 결론은 맞았지만 확인 절차가 없었다. 시나리오 15와 같은 부류.

### 시나리오 18: "내가 회의 선호 시간 적어둔 거 뭐였지?"
- trace: `search_personal_references(query="회의 선호 시간")` → 4건, `retrieval.sufficient = true`
- 판정: 통과
- 관찰: 4주차 참고자료 검색으로 갔다. 5주차 MCP tool로 새지 않았다(주차 간 경계 유지).

### 시나리오 19: "내일 오후 3시에 팀 회의 저장해줘"
- trace: `extract_schedule_request` → `save_structured_request` → `shared_sync: created`
- 판정: 통과
- 관찰: 3주차 저장 경로로 갔고 5주차 `create_shared_schedule`로 새지 않았다. 앱 저장과 함께 공유 저장소 동기화가 자동으로 일어나는 것도 확인했다.

### 시나리오 20: "공유 저장소에 2026년 7월 20일 14시 스터디를 영희 이름으로 등록해줘" → "방금 등록한 거 삭제해줘"
- trace(등록): `create_shared_schedule(member_name="영희", title="스터디", date="2026-07-20", start_time="14:00")` → `schedule_id: shared_efdc067e9b`
- trace(삭제): **tool 호출 없음**
- 답변: "일정 ID를 알려주시면 삭제해 드리겠습니다."
- 판정: **실패**
- 관찰: 바로 앞 turn의 tool 결과로 `schedule_id`를 받았는데 사용자에게 되물었다. 등록할 때 `source_conversation_id`도 남기지 않아(`null`) 출처로 찾을 수도 없다.

## 1차 조치와 재측정

발견한 실패를 프롬프트 규칙으로 옮기고 같은 입력으로 각 2회 재측정했다.

| 규칙 | 내용 | 대상 | 재측정 |
| --- | --- | --- | --- |
| ⑩ 보강 | query는 짧은 핵심어 하나. 0건이면 더 짧은 키워드로 재검색 | 10·12 | **미준수 2/2** |
| ⑫ 보강 | member_names에는 외부 멤버만. 내 일정은 자동 포함 | 5 | **교정 2/2** |
| ⑫ 보강 | 내 것만 보려고 같은 tool을 다시 부르지 않는다 | 5 | 미준수 2/2 |
| ⑭ 보강 | 대화에서 얻은 일정을 "확정됐다"고 말하지 않고 공유 저장소로 확인 | 10 | **준수 2/2** |
| ⑰ 신규 | 조회 없이 단정하지 않는다. 앞 답변을 근거로 새 질문에 답하지 않는다 | 15·17 | **교정 2/2** |
| ⑱ 신규 | 대상 미지정 질문을 앞 대화 멤버로 좁히지 않는다 | 16 | **교정 2/2** |
| ⑲ 신규 | 받은 schedule_id를 삭제에 그대로 쓴다 | 20 | **교정 2/2** |
| ⑲ 신규 | 등록 시 source_conversation_id를 남긴다 | 20 | 미준수 2/2 |

### 시나리오 10이 교정된 경로

재측정에서 검색 질의는 여전히 `"7월 9일 철수"`였고 **rows는 0건**이었다. 그런데도 답은 정확했다. 규칙 ⑭이 "확정 여부는 `list_shared_schedules`로 확인하라"고 지시했고, 그 일정이 공유 저장소에 등록되어 있어 거기서 근거를 찾았기 때문이다.

즉 **질의 표현 문제는 그대로이고 우회로가 생겨 결과만 맞아진 것**이다. 시나리오 12처럼 대화 내용에만 있고 일정표에는 없는 정보를 물으면 여전히 0건으로 끝난다.

### 프롬프트로 교정되지 않은 것

`"0건이면 반드시 한 번 더 검색한다"`를 명령형으로 적었지만 두 번의 재측정에서 모두 지켜지지 않았다. 4주차에서 관찰한 "프롬프트로 재검색을 강제할 수 없다"가 5주차에서도 같은 형태로 나타났다. 이번에는 원인을 **부분 문자열 대조**로 특정했다는 점이 다르다.

이 시점에는 한계로 단정하지 않고 관측만 남겼는데, 이후 같은 내용을 tool docstring으로 옮겨 해결했다(아래 "반복 교정 기록" 참조).

## 검증 중 발견한 데이터 오염과 그 원인

시나리오 16을 재측정하던 중 답변에 "저는 11:00부터 개인 코칭 일정이 여러 건 있습니다"가 나왔다. 앱 DB를 조회했을 때 해당 구간에 일정이 0건이어서 처음에는 환각으로 판단했으나, **공유 저장소를 확인하니 실재하는 row였다.**

```
member_name="나", title="[오프라인검증] 개인 코칭", date=2026-07-17  → 12건
```

공유 저장소 63건 중 45건이 테스트 잔여물이었다.

| 건수 | 제목 | 출처 |
| --- | --- | --- |
| 12 | `[오프라인검증] 개인 코칭` | 3주차 오프라인 검증 하네스 |
| 9 | `회귀검증 팀 리뷰` | 4주차 e2e 회귀 fixture |
| 6 | `치과 정기검진` | 4주차 e2e 저장 흐름 입력 |
| 5 | `안정성검증 스트레칭` | 테스트 |
| 7 | `스터디` / `[E2E] 스터디` | 4주차 e2e |
| 3 | `[E2E] 병원 예약` | 4주차 e2e |

## 자동 하네스 도입과 조건 정정

같은 20개를 반복 측정하기 위해 판정 하네스를 만들었다. 처음에는 앱과 결과가 달라, 이력을 넘기는 방식을 확인했다.

- 앱(`fixed/agent_runtime.py:_agent_messages`)은 이력에 **user/assistant 텍스트만** 넘기고 tool 호출·결과는 넘기지 않는다.
- 하네스는 tool 메시지까지 넘기고 있었다. 그래서 agent가 앞 턴의 tool 결과를 그대로 보고 재조회를 생략해, 앱에서는 통과하던 3·4·5가 실패로 나왔다.
- 하네스를 앱과 같은 조건으로 맞춘 뒤에야 실제 동작이 재현됐다.

**배운 것**: 재현 환경이 실제와 한 군데라도 다르면 없는 실패를 쫓게 된다. 측정 도구부터 실제와 맞는지 확인해야 한다.

### 시스템 프롬프트보다 docstring이 효과적이었던 사례

12번은 시스템 프롬프트에 같은 취지를 두 번 적어도 3/4에 머물렀다. 같은 내용을 **tool의 docstring**으로 옮기자 5/5가 됐다. docstring은 tool을 고르고 인자를 채우는 시점에 함께 읽히기 때문으로 보인다. 인자 형식을 교정할 때는 시스템 프롬프트보다 docstring이 가까운 자리다.

### 시나리오 5의 판정 기준을 바꾼 이유

프롬프트를 세 번 강화하고 docstring까지 손봤지만 `member_names=[]`인 중복 호출이 약 1/3 확률로 남았다. 그 경우의 답변을 직접 확인했더니 **항상 정확했다.**

```
- 나: 이 기간에 등록된 바쁜 일정이 없습니다.
- 철수: 7월 7일 10:00-11:00 API 연동 실습 / 7월 9일 14:00-15:30 고객 인터뷰 / 7월 15일 16:00-17:00 QA 리뷰
```

즉 중복 호출은 **오답이 아니라 MCP 서브프로세스 한 번의 낭비**다. 그래서 판정 기준을 "정확히 1회 호출"에서 "비서 이름이 섞이지 않고 답변이 내 일정과 외부 멤버 일정을 정확히 구분할 것"으로 바꿨다. 기준을 조용히 낮추지 않기 위해 이 판단을 여기에 남긴다. 중복 호출 자체는 미해결 관측으로 둔다.

## 규칙을 docstring으로 옮기기

12번이 시스템 프롬프트로는 3/4였다가 docstring으로 옮기자 5/5가 된 것을 보고, 옮길 수 있는 규칙을 정리했다.

**기준**

| | 담을 것 | 읽히는 시점 |
| --- | --- | --- |
| tool docstring | 이 tool 하나를 어떻게 쓰는가 — 인자 형식, 반환 의미 | tool을 고르고 인자를 채울 때 |
| 시스템 프롬프트 | 여러 tool 중 무엇을 언제 고르는가, 답변을 어떻게 쓰는가, 대화 맥락을 어떻게 다루는가 | 전체 판단 |

**옮긴 것**

| 갈 곳 | 내용 |
| --- | --- |
| `search_previous_conversations` | `member_names` 생략(전체)과 빈 목록(0건)의 차이 |
| `extract_schedules_from_history` | `member_names` 필수, 빈 목록은 0건이므로 대상을 먼저 확인 |
| `list_shared_schedules` | 필터가 없으면 기본값으로 대체되므로 날짜를 임의로 채우지 말 것 |
| `collect_member_schedules` | 외부 멤버만, 질문 하나에 한 번, "각각"은 답변을 나누라는 뜻 |
| `create_shared_schedule` | `source_conversation_id`를 남길 것, UPSERT 의미 |

프롬프트 규칙은 ⑨~⑲ 11개에서 ⑨~⑱ 10개로, 분량은 2,788자에서 2,115자로 줄었다.

### 이 과정에서 나온 두 가지

**중복이 도움이 되는 경우가 있었다.** 검색 질의 규칙을 docstring에만 남기고 프롬프트에서 지웠더니 12번이 전체 실행 3회 중 1회 실패로 돌아갔다(`"발표 리허설 준비"`에서 `"준비"`를 떼지 못함). 문단 전체를 되돌리지 않고 핵심 한 문장만 프롬프트에 복원하자 다시 통과했다. 같은 제약을 두 곳에 두는 것이 항상 낭비는 아니다.

**지시를 나눠 적으면 앞의 것만 따른다.** "원문을 요구하면 반드시 load_conversation_messages를 부른다"와 "conversation_id는 검색 결과에 있던 값을 쓴다"를 따로 적었더니, 3번이 3회 중 2회 실패하며 `convo_철수_2023` 같은 **id를 지어냈다.** 앞 지시를 따르느라 검색을 건너뛴 것이다. "먼저 검색으로 id를 찾고, 그 id로 load를 부른다"처럼 한 문장으로 묶자 3회 모두 통과했다.
