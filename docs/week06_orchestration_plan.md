# Week 6 — supervisor 위임 구조 plan (실측 기반 의사결정 기록)

대상: `student_parts/week06_kanamate_decides_schedule.py`
검증 자산: `.claude/skills/verify-week6/SKILL.md` (14단계), `evals/week06_eval.py` (30축)
최종 baseline: **150/150** (30축 중 critical 19, n=5, 시계 2026-07-06 고정)

이 문서의 핵심은 통과 수치가 아니다. **내가 만든 판정이 내가 만든 정상 동작을 7번 FAIL시켰다**는 기록이다.
프롬프트 결함 4건보다 판정 버그 7건이 더 많았고, 그중 3건은 원인이 하나였다.

## 1. 진행 구조 결정 — 회차 분리 기각

가이드는 메인/추가 2티어로만 나뉘고 명시적 회차 표기가 없다. 처음에는 티어 경계를 회차 경계로 삼아
"1회차 구현 → 커밋 → 2회차" 를 제안했으나, 사용자가 **동시 구현**을 택했다.

결과적으로 옳았다. `kana_tools()`(week06:429-439)에 추가 과제 tool 2개가 이미 들어 있어, 회차를 나누면
목록에서 빼고 2회차에 되넣는 편집 왕복이 생긴다. Kana prompt의 연쇄 호출 지시(`③④`)도 두 커밋에
걸쳐 쪼개져야 했다. 동시 구현으로 그 왕복이 전부 사라졌고, 커밋만 논리 단위로 나눴다.

## 2. 재사용 리뷰 — 5주차 반성이 작동했다

`/simplify`를 verifier **전에** 돌리는 게이트가 이번에 값을 냈다. builder가 정의한 새 함수는 **0개**였고
(재사용 자산표를 명세에 넣은 효과), 리뷰 4축이 잡은 것 중 실행 가능한 것은 다음이었다.

- 위임 wrapper 두 개의 4키 계약 중복 → `_subagent_payload` 하나로 (2개 리뷰가 수렴)
- supervisor prompt에서 "가장 강한 제약" 이중 선언 + 위임·근거 규칙 중복 (2개 리뷰가 수렴)
- 도달 불가 방어 코드 `busy_rows or []`

**반영하지 않은 것과 근거:**
- `extract_agent_events` → `fixed`의 `extract_langchain_trace`(base) 교체: 가이드 line 62가
  `extract_agent_events()`를 명시적으로 지정한다. 이득이라던 `structured_response` 보존은 하위 agent에
  `response_format`이 없어 실현되지 않는다.
- description·Kana prompt 길이 축소: **정적 분석만으로 프롬프트를 줄이지 않는다.** trace/eval로만 판정한다.

## 3. altitude 리뷰가 정적으로 잡은 실제 결함 3건

이 세 건은 "코드가 스펙대로인가"가 아니라 **"프롬프트가 지시하는 호출이 스키마와 맞는가"** 를 대조해 나왔다.
verify로도 eval로도 안 잡히는 층이다.

| # | 결함 | 결과 |
|---|---|---|
| 1 | Kana 절차 ③과 예시가 `find_common_available_slots`를 `candidate_slots`+`busy_rows`만으로 부르라고 지시 | `member_names`/`date_from`/`date_to`가 필수 필드라 pydantic 검증 실패 → 턴 낭비 후 범위를 창작 |
| 2 | 절차 ④가 `candidate_slots`를 빼고 부르라고 지시 | `candidates`가 `[]`가 되고 근거 키 전부 소실. `selected_index=0`이 빈 목록을 가리켜 `invalid_selection`이 되는데 `reason`을 함께 넘겨 그 경고가 덮여 **완전히 조용히** 실패 |
| 3 | 누적된 week05 마지막 문장이 Week 6의 핵심 산출물을 금지 | "여러 사람의 최종 회의 시각 확정은 하지 않는다"가 supervisor prompt에 그대로 실림 |

3번의 교훈: **override는 도구 지시만이 아니라 역할 범위 선언까지 들어올려야 한다.** 처음 작성한 override
문단은 스스로를 "앞의 도구 지시와 인자 규칙"으로 한정했고, 역할 금지는 그 범위 밖이라 살아남았다.

함께 반영: description에 `fixed/schedule_decision.py`가 **사유 없이** 적용하는 게이트를 명시했다 —
후보 `date`의 범위, **최상위** `duration_minutes`가 길이 필터(항목 값이 아님), `"미정"`/빈 `end_time`의
하루 차단. 셋 다 탈락 이유가 반환되지 않아 "빈 시간 없음" 오답으로 이어진다.

## 4. 판정 버그 7건 — 이 주차의 본론

전부 **정답의 모양을 정해두고 검사**한 결과다(`kanana-conventions` §6이 경고하는 그것). 목록:

| # | 축 | 무엇을 정답으로 박았나 | 실제 정상 동작 |
|---|---|---|---|
| 1 | 라우팅 6축 | `supervisor_selected_agent == "..."` | 마지막 위임만 기록되므로, 조율 후 저장처럼 두 번 위임하면 `nana_agent`로 보인다 |
| 2 | `final_slot_matches_answer` | 답변에 `YYYY-MM-DD` 또는 `M월 D일` | 답변은 `"7일(화) 오전 9시"` |
| 3 | `kana_defers_saving` | 어간 `"저장했"` | `"제가 저장했다고는 말씀드리지 않습니다"` — **부정문 안의 어간** |
| 4 | `final_slot_in_requested_week` | 확정 실패도 이 축의 실패로 | 한 축이 두 가지를 재고 있었다 |
| 5 | `no_invented_final_slot` (seed) | 09:00–18:00만 막음 | `18:00–19:00` 제안이 정답 — 저녁 요청에 workday를 넓히는 건 다른 축이 요구하는 동작 |
| 6 | `kana_chain_to_decide` | `[find, decide]` 인접 순서 | `[collect, find, find, decide]` — `③-b`가 지시한 재호출 |
| 7 | `agent_fills_candidate_slots` | **첫** find 호출의 `candidate_slots` | 첫 호출이 비고 재호출이 채우면 결과는 정상 |

### 4-A. 같은 프롬프트 규칙이 두 축을 동시에 깼다 (가장 큰 반성)

6번과 7번은 **원인이 하나**다. 내가 추가한 `③-b`("0건이 돌아왔으면 후보를 다시 골라 한 번 더 호출한다")가
재시도를 정당한 경로로 만들었는데, 두 판정은 단일 호출을 정답으로 박아둔 채였다.

더 나쁜 것은 **6번만 고치고 7번을 실제 결함으로 오해했다**는 점이다. 7번을 두고 "프롬프트를 더 밀어붙일지"
사용자에게 물었고, CoT 레버까지 동원한 뒤에야 판정 버그임을 알아봤다.

→ **규칙: 프롬프트에 재시도·대안·예외 경로를 넣으면, 그 경로를 인정하도록 판정을 같이 넓힌다.**
프롬프트와 판정은 같은 커밋에서 함께 움직여야 한다.

### 4-B. 하네스 버그 2건

- `compare()`가 통과 **횟수**를 비교했다. n=3 baseline과 n=5 실행을 비교하니 변하지 않은 축 26개가
  전부 `"↑ 3 -> 5"`로 찍혀 **나는 그것을 개선으로 보고했다.** 통과율 비교 + n 불일치 경고로 고쳤다.
- 관측 축의 note는 실패 시에만 출력된다. `specific_time_request`가 5/5로 통과하자 관측하려던
  체인 상태를 볼 수 없었다. **미해결.**

## 5. 프롬프트 결함 4건 — 전부 측정으로 잡았다

| 결함 | 발견 경로 | 통과율 |
|---|---|---|
| 주제 없는 대화 검색에서 되묻고 멈춤 | eval | 0/3 → 3/3 |
| 이름 창작 회귀 | eval (내 수정이 만든 회귀) | 3→2/3 → 5/5 |
| "이번 주"를 지난 주로 계산 | **앱 실행** | 신규 축 5/5 |
| 조회 결과만으로 확인을 되물으며 체인 중단 | **앱 실행** | 40% → 100% |

### 5-A. 내 수정이 회귀를 만들었고 eval이 잡았다

1번을 고치려고 넣은 문장이 두 가지를 잘못했다. ⓐ 예시에 `철수`라는 **복사 가능한 실제 이름**을 넣었고
(builder는 이 오염을 피해 `"<날짜>"` 자리표시자를 썼는데 내가 되돌렸다), ⓑ "되묻지 않는다"를 주제가 아니라
요청 전체로 일반화해 바로 위 규칙과 충돌시켰다. 되묻는 기준을 **주제/이름으로 분리**해 해결했다.

### 5-B. 금지문 3회차보다 성격이 다른 레버 1회

`candidate_slots` 미기입은 description 금지문 + 절차 강화로도 60%에 머물렀다. 같은 종류를 더 얹는 대신
**CoT 강제**(`②-b`: ③을 호출하기 전에 후보를 `'날짜 시작-종료 (근거)'` 한 줄씩 **글로 적고** 그 값을 옮긴다)로
바꾸자 100%가 됐다. 금지가 안 먹히면 강도를 올리기보다 **추론 산출물을 먼저 만들게 하는 쪽**을 시도한다.

## 6. 앱 직접 실행이 필수인 이유 — 이번에도 증명됐다

`verify-week6` 14/14 + eval 통과 **이후에** 앱에서 결함 2건이 나왔다. 둘 다 각 단계가 자기 계약을 지키면서
조용히 틀리는 유형이라 결정적 검증으로는 원리적으로 안 잡힌다.

1. **"이번 주"를 지난 주로 계산** — 엉뚱한 주를 조회해 busy_rows가 0건이 되고, 후보가 전부 과거 날짜인데
   겹칠 것이 없어 전원 통과하고, 결국 `2026-06-29`를 회의 시각으로 확정 통보했다.
   기존 축이 못 잡은 이유: `busy_time_not_proposed`는 겹침만, `final_slot_matches_answer`는 payload와
   답변의 일치만 본다. **둘 다 통과하면서 답변은 지난 주 이야기였다.**
2. **체인을 ①에서 끊고 "이 시간으로 확정할까요?"** — `collect` 하나만 부르고 산문으로 후보를 제안했다.
   검증도 기록도 없어 `final_slot_payload`가 null. 겹침 판단을 눈대중으로 대신한 것이다.

### 6-A. 앱 시계와 eval 시계가 다르다는 것 자체가 사각지대다

eval은 `2026-07-06`으로 고정한다(July fixture `07-07~07-17`이 미래여야 "이번 주" 질문이 데이터에 걸린다).
앱 실제 시계는 그보다 뒤라 **같은 fixture가 과거**다. 날짜 관련 동작은 두 환경에서 다르게 움직인다.

실제로 그 틈에서 하나가 관측됐다: 앱에서 `2026-07-14`(당시 기준 약 3주 과거)를 회의로 확정하고 저장했다.
Kana prompt에 "지나간 날짜를 후보·최종 시각에 쓰지 않는다"는 규칙이 있는데 지켜지지 않았다.
**eval은 이걸 원리적으로 못 잡는다** — 시계 고정 때문에 `07-14`가 미래다.

→ **테스트 산물로 분류하고 고치지 않았다.** fixture를 보려면 7월 날짜를 쓰라고 내가 안내한 결과이고,
실사용에서 과거 날짜로 회의를 잡을 이유가 없다. 다만 **"eval이 시계를 고정하는 대가로 생기는 사각지대"** 는
다음 주차로 넘긴다(§8).

## 7. 범위 밖으로 분류한 것 (고치지 않음)

- **`IntegrityError: UNIQUE constraint failed: schedules.schedule_id`** — eval에서 간헐적으로 나고
  실행마다 **다른 축에 무작위로 꽂혀** 게이트를 흔들었다. **원인 미규명.** 확인한 것: `new_id`는 uuid4라
  충돌 불가, 앱 `schedules` INSERT 경로는 `fixed/app_store.py:356` 한 곳뿐이고 중복 가드가 있고,
  단순 중복 `source_schedule_id`는 `existing: True`로 정상 처리되며, 외부 저장소는 `ON CONFLICT DO UPDATE`라
  무관하다. 라이브 6회 재현 실패. 위치가 읽기 전용 `fixed/`라 고칠 수도 없다.
- `kind: personal_schedule`에 `members: [철수, 영희]`가 들어가 참석자별 공유 row가 안 생기는 것 — week03 의미론.
